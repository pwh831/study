# 교과 암기 퀴즈

`Jiri`(지역이해)와 `Japan`(일본어 단어시험)에서 두 번 검증된 틀을 과목에 상관없이 쓸 수 있게
뽑아낸 것이다. **엔진은 이미 다 되어 있다. 할 일은 데이터를 채우는 것뿐이다.**

## 언제 쓰나

학습지·교과서·단어장처럼 **외워야 할 항목이 정해져 있는** 범위를 반복 학습 앱으로 바꿀 때.

안 맞는 경우: 계산 문제, 서술형 논술, 풀이 과정이 정답인 과목. 이 엔진은 "항목 ↔ 서술"을
양방향으로 묻는 도구이지 문제 풀이 도구가 아니다.

## 원칙 — 이것부터 읽는다

1. **엔진은 과목마다 고치지 않는다.** `index.html` 은 `data/items.js` 만 읽는다.
   화면 문구까지 데이터가 정한다(`SUBJECT.kind`, `CATS[].kind/what`). 엔진을 고쳐야 할 것
   같으면 거의 언제나 데이터 설계가 잘못된 것이다. 정말 엔진 문제라면
   **스킬의 원본**(`.claude/skills/quiz/assets/index.html`)을 고치고 과목 폴더에 다시 복사한다.
   과목별로 엔진이 갈라지면 고친 것이 한쪽에만 남는다.
2. **서술은 지어내지 않는다.** 학습 자료에 있는 문장을 옮긴다. 자료가 없으면 먼저 달라고 한다.
   자료 없이 교육과정 일반 지식으로 채웠다면 **그 사실을 README 와 사용자에게 분명히 말한다.**
3. **답이 새어 나가지 않게 한다.** 서술 안에 그 항목의 이름을 쓰지 않는다.
   ("몽타주 — 몽타주는 쇼트를 이어 붙여…" 는 못 쓴다.)
4. **파일 하나로 돌아야 한다.** 태블릿에서는 폴더째 옮기는 길이 막혀 있다.
   `build.py` 산출물이 진짜 배포본이고, 그것이 열리는지 확인해야 끝이다.
5. **헷갈리는 짝을 가르는 것이 시험이다.** `confuse` 를 걸면 오답 보기를 거기서 먼저
   길어온다. 이걸 안 걸면 보기만 보고 답이 보여서 정작 시험에서 가르지 못한다.

## 만드는 순서

### 1. 범위를 확보한다

사용자에게 **학습지·교과서·단어장 원본**(PDF·사진·붙여넣은 글)과 **시험 범위**(몇 쪽부터
몇 쪽까지)를 받는다. 기출이 있으면 함께 받는다 — 어떤 유형으로 나오는지가 데이터 설계를 바꾼다.

자료를 받기 전에 데이터부터 쓰기 시작하지 않는다. 다만 **자료를 기다리는 동안 구조
(AREAS·UNITS·CATS)와 앱 껍데기는 먼저 세워도 된다.**

### 2. 폴더를 만든다

```bash
mkdir -p subjects/<과목>/data
cp .claude/skills/quiz/assets/index.html  subjects/<과목>/
cp .claude/skills/quiz/assets/build.py    subjects/<과목>/
cp .claude/skills/quiz/assets/verify.js   subjects/<과목>/
cp .claude/skills/quiz/assets/smoke.js    subjects/<과목>/
cp .claude/skills/quiz/assets/data/items.js subjects/<과목>/data/
```

`index.html`·`build.py`·`verify.js`·`smoke.js` 는 **그대로 둔다.** 고치는 것은 `data/items.js` 뿐이다.

### 3. 구조를 먼저 짠다

항목을 쓰기 전에 `SUBJECT`·`AREAS`·`UNITS`·`CATS` 를 짠다. 학습지의 대단원 구조를 그대로
따르는 것이 제일 좋다 — 사용자가 "3단원만 풀래" 라고 생각하는 단위가 그것이기 때문이다.

- `AREAS` — 성격이 다른 큰 덩어리 (한국지리/세계지리, 영상 언어/서사/비평…)
- `UNITS` — 학습지 단원. 번호(`no`)는 학습지 번호를 그대로 쓴다
- `CATS` — 단원 안의 세부 갈래. 한 세션에 풀 만한 크기(10~30항목)로 자른다
- 시험 범위 밖 단원은 지우지 말고 `exam:false` — 자료는 남기되 처음엔 선택되지 않는다

갈래마다 문제문에 쓸 말이 다르면 `kind`("이 <용어>의 이름은?")와 `what`("…의 <뜻>을")을 넣는다.

### 4. 항목을 채운다

자세한 계약은 `references/data-schema.md`, 서술을 어떻게 쓰는지는
`references/question-types.md` 를 읽는다. 요점만:

- `features` 는 한 항목당 **2~4개**. 하나뿐이면 '설명 고르기'와 '설명 → 이름'이 매번 같은
  문장으로 나온다. 다섯을 넘으면 '떠올리기'가 사실상 불가능해진다
- 각 서술은 **그 항목에만 해당해야** 한다. 여러 항목에 해당하는 문장은 '설명 → 이름'의
  답을 둘로 만든다 (`verify.js` 가 겹침을 WARN 으로 잡아 준다)
- 이름의 다른 표기는 전부 `aliases` 에 (`클로즈업` / `클로즈 업` / `C.U.`)
- 시험에서 가르기 어려운 짝은 서로 `confuse` 로 건다 (양방향으로)
- 각주·심화처럼 범위 밖이지만 나온 적 있는 서술은 `notes` 에 (기본 출제 제외)

### 5. 검사하고 빌드한다

```bash
cd subjects/<과목>
node verify.js      # 데이터 계약 — ERROR 가 하나라도 있으면 고친다
python3 build.py    # → 단일 HTML (문법 검사 포함)
node smoke.js       # 진짜 브라우저로 한 세션을 끝까지 풀어 본다
```

`verify.js` 의 ERROR 는 전부 고친다. WARN 은 판단해서 남길 수 있지만 **왜 남기는지 말한다.**

### 6. 실제로 열어 본다

`smoke.js` 는 다섯 유형이 다 나오는지, 보기가 5개인지, 진도가 새로고침을 넘어 남는지,
휴대폰 너비에서 가로 스크롤이 안 생기는지를 본다. 그래도 **눈으로 한 번은 연다** —
문제문이 말이 되는지, 조사가 어색하지 않은지는 기계가 못 본다.
나머지는 `references/checklist.md`.

### 7. README 와 PRD 를 쓴다

`subjects/<과목>/README.md` — 무엇을 어떻게 외우는 앱인지, 범위가 어디까지인지,
데이터를 어디서 가져왔는지, 항목 추가 방법. **자료 없이 채운 부분이 있으면 여기 적는다.**

## 데이터를 고칠 때

항목 추가는 `ITEMS` 에 객체 하나. 새 갈래는 `CATS` 에 한 줄 + 그 단원의 `cats` 에 키 추가.
고친 뒤에는 **반드시** `node verify.js && python3 build.py` 를 다시 돌린다 — 산출물은
빌드해야 갱신된다. 빌드를 안 돌리면 사용자는 옛 앱을 계속 본다.
